## Meeting with Gregor Richards - September 25, 2026 (10:00 am)
Notes from Gregor Richards' comments:
- [After describing our abstract] What is the goal of readability / quality of the transpiled code? If you turn Python into C and it does run, it is a much easier goal than it being something you can maintain after, and easier than being able to to then also later take it after and turn it into Java. Fundamentally they're all Turing complete so it's all 'possible'. Wherever you bridge the gap of semantic differences (e.g., Python list vs Java array), you need to make a choice (e.g., create a library to handle each kind of weird thing, looks less idiomatically to that language but still preserves the correctness). Maybe worth using AI to dynamically bridge these gaps: maybe not necessarily for this project, but likely will be what'll need to be done in the future (either have the AI makes those kinds of decisions, or it becomes a more interactive process where the user decides what to do for each library).
- [We except our transpiler to create an initial migration that does something at least] If that's the goal, the top requirement is somewhere between readability and idiomatic compatibility with the target language: makes the semantic gap more of a hazard rather than less. If you want to use that code in the future, you wouldn't want it to be non-idiomatically in that program language. The real difficulty is that if you want a central hub/IR, seemingly no obvious way for that central IR to expand to glob on every important idiom from every language. Differences between families of languages will be gigantic. Will be good to decide what your limits are. Maybe a certain level: e.g., not C++, only JavaScript or Python. Philosophically impossible to merge between certain levels: there are many wacky programming languages that will make this hard. Semantic gaps will still be there if you limit yourself, but smaller and easier to tackle. What they don't know and we'll need to investigate is are there semantic gaps between each pair of languages.
- [Some tools use a mix of determinstic process with LLM translation- is this worth exploring?] In my life, I've been lured by the temptation of determinism and I feel it's overrated. Programming is a creative task: the creation of the program was not determinstic in the first place. The more the input is a dynamic product of creativity, the less determinstic is helpful for an output. Maybe a more approachable technique is having a determinstic translation step that makes weird non-idiomatic code and have an AI generate suggested edits that you either agree/disagree/discuss further with the AI. Probable goal is you do have some shim libraries that get injected for certain idioms used elsewhere (maybe this is done in the middle level of the IR, then you don't have to make it in the target language).
- [What is a realistic goal for us to get feasible results in 1.5 years?] Either aim for a somewhat diverse but not enormous range of languages but all the same sort of level (e.g., Haskell at the level of C/C++): either choose rougly all either the same level (all untyped or optionally typed: another axis to fight)- try to be a bit more broad than just 'imperative languages', OR try to do a stack of like Python/Rust/C++ across levels (same level different paradigms probably easier than different level same paradigms). If too narrow across both axis, then not really too impressive.
- [Worth going for either interesting pairs e.g., memory unsafe to memory safe?] This sounds like another project. For this, you'd ideally pick languages as similar to each other on every other access and that'd be the sole thing you're attacking. Doesn't really fit what you described to be 10 minutes ago. Handling anyone of those narrow and precise goals is a project on its own, but it seems perhaps your ideal is that regardless of your reason to move from X to Y, we can handle that move, which is a more generalizable approach. In a perfectly ideal world (so not what will happen), the project you're describing could be a general foundation where, when company X wants to migrate languages, they can do that- a central hub IR is the defining feature of your more generalizable vision you have. Moving for a particular goal (e.g., memory safety) will be a different kind of project.
- [What about if we had multiple 'hub' IRs for each type of language instead of a single big 'hub' IR?] In a typical language, your IR includes things at many different levels and as you go through compilation steps, your IR no longer includes certain information (e.g., using this field of this object converts into access this memory address). Rather than see it as different hubs, perhaps better to see it as there being a core of stuff like 'addition' and that core has tumors in other directions that are really more suitable for different language types, where you don't have a way to convert those IR instructions into other languages, so you're making decisions based on your source and target on what compilation steps need to be done and what needs to be changed. You can look for patterns in the core that are idioms that ought to be represented when you move them back out again. Approach it more like an IR with different categories of instructions in it, with instructions more or less suitable for different kinds of langauges, rather than different IRs.
- [What axis' shuld we look into? Paradigm/level, another prof mentioned garbage collection. What should we focus on?] If you look for many axis, you will find many, but some matter more. A lot of the high vs low level difference is how you interact with data. There are like 6 programming languages without garbage collection and all the others do, so while this axis exists, it is probably not the most important one to look at. A lot of the different axis mesh very well with level as a broad idea and paradigm. Most things imperfectly but more or less map in those two axis. Diversity here shouldn't be too extreme: programming languages far younger than other languages.
- [Any other past work/research we should look into on our kind of thing? Can only find transpilers that do 2 specific languages online.] I believe genuinely there isn't very much taht is similar to what you're discussing. Transpilers usually are just a pair. The most similar concept is not in transpilation of languages but in polygot/multilanguage virtual machines (e.g., the .NET virtual machine- ZLR: main goal was C# but should be suitable for other languages like F#, C++, Visual Basic). The closest you're likely to fine is multilanguage virtual machines which don't have the goal of translating between languages but do have the goal of the 'hub IR' that can support a bunch of paradigms and programming langauges. The closest you'll find for multi-language transpilers are like coincidence ones, where you can combine transpilers that weren't designed to work together but you could technically combine (e.g., you can compile C to Web Assembly and Web Assembly to JavaScript to get a C to JavaScript conversion: though it looks like madness). I'm sure somebody has explored your goal to a certain extent, but I don't know any major noteworthy projects doing that.
- [Can we reach out again for advice/help etc.?] Yes! Note on roadblocks: you should set a high goal and expect failure. Find a goal where getting 80% of it, it's still good, rather than one where getting 80% of it is still bad (or 60%, 40%: whatever your goal). You should have an unrealistic goal and strive to achieve it, though go into it knowing you expect to encounter failures. You can contact me about that goal and how you adjust it, and I'll let you know if it's what I think you should strive for and what you should go for.
